# Wildbuds

**Wildbuds** is a tactical, peer-to-peer, turn-based strategy game. It blends grid-based positioning, deep elemental combat, and a highly tactical action economy into a competitive multiplayer experience.

## Game Goals

The core objective of Wildbuds is to provide a deterministic, highly tactical combat experience where every decision matters. Players command a team of distinct units on a square grid, attempting to outmaneuver and exploit the elemental weaknesses of their opponent's team. 

Key design pillars include:
- **Deep Elemental Combat**: Units possess distinct base stats and dual-typings. Combat relies on an elemental matrix where exploiting weaknesses (and avoiding resistances) is key to victory.
- **Tactical Action Economy**: Instead of moving an entire army at once, the game uses an alternating activation system. Players must carefully prioritize which unit to activate and when.
- **Deterministic Peer-to-Peer**: The game is designed from the ground up for seamless P2P multiplayer, relying on lockstep deterministic resolution so that all players always share the exact same authoritative board state.

## Expected Gameplay Loop

1. **Match Initialization**: Players connect directly to one another and the board state is initialized.
2. **Alternating Activations**: The core loop operates on strict, alternating unit activations. 
   - Player One selects a single unit to activate.
   - The activated unit spends its available action tokens (e.g., Move, Attack, Special).
   - Once the unit ends its activation, authority passes to Player Two.
3. **Execution**: Attacks and abilities are resolved according to the elemental matrix and unit stats.
4. **End Conditions**: The activation cycle continues back and forth until all units have acted (completing a Round), or a player achieves the victory condition (e.g., routing the opponent's team).

## Architectural Structure

To guarantee perfectly synchronized multiplayer without a central server, the game's architecture is built on a strict **Command-First, Authoritative Resolution** pattern.

- **Presentation / Input Layer**: The user interface (cursor, mouse clicks, keyboard presses) only manages local visual state. It never directly mutates the game board. Instead, it interprets user intent and emits discrete *Commands* (e.g., `SelectUnit(x, y)`, `MoveUnit(x, y)`).
- **Network Transport Layer**: Commands generated by the local player are pushed into an outgoing queue, serialized, and transmitted over the network to all connected peers (including a loopback to the local client).
- **Authoritative Resolver**: An internal queue receives the synchronized stream of commands from all players. A deterministic resolver validates each command (checking turn authority, unit ownership, and rule legality) before mutating the actual authoritative game state.
- **Observation**: The rendering and audio systems simply observe the authoritative game state and update the screen accordingly.

This complete separation of presentation, transport, and game logic ensures that cheating is difficult and desynchronization between peers is mathematically impossible as long as the ruleset remains deterministic.
